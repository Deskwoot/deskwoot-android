# Deskwoot Android SDK: architecture

A native visitor chat client of Deskwoot's public widget API (`/api/widget/*`), not a WebView. The iOS SDK is its mirror image: same layers, same names, same behaviour, same tests. It speaks the widget API the way Deskwoot's web messenger does and follows the same rules.

## Layers

```
Deskwoot (public facade)                 Deskwoot.kt, DeskwootUser.kt
  └─ ChatSession                         engine/ChatSession.kt      one per widget token, lives for the process
       ├─ WidgetApi                      api/WidgetApi.kt           a typed call per endpoint, answers in api/Answers.kt
       │    └─ HttpClient                api/HttpClient.kt          one request function, ApiResult = Success | Failure(ApiError) | NetworkFailure
       │         UrlConnectionHttpClient api/UrlConnectionHttpClient.kt
       ├─ RealtimeClient                 realtime/RealtimeClient.kt
       │    AblySseClient                realtime/AblySseClient.kt  Ably over SSE, no Ably SDK (SseParser.kt, EventStream.kt)
       ├─ VisitorStore                   store/VisitorStore.kt      bearer and markers, JSON in noBackupFilesDir/deskwoot/
       ├─ DiskCache                      store/DiskCache.kt         config, list and last thread for an instant first paint
       ├─ ConversationEngine             engine/ConversationEngine.kt  the state machine of one visitor
       │    └─ PushRegistrar             engine/PushRegistrar.kt    this phone's push registration for the visitor
       └─ HelpCenterClient               help/HelpCenterClient.kt
Models (immutable)                       model/*.kt
```

The UI (section "UI" below) reads `ChatSession.state` (a `StateFlow<SessionState>`) and calls its actions:

`start`, `refresh`, `stop`, `setVisible(threadOnScreen)`, `setForeground`, `openConversation(id)`, `ownsConversation(id)` (true once the restore, the list or a write of this visitor named it, false once the visitor settled and nothing did, null before, also while a stored verified user waits for `identify`: the in app card's conversation opens only on true), `pushVisitor(key)` (whose a push's visitor key is: `ACTIVE`, `DORMANT` or `FORGOTTEN`; any thread), `openTapped(id)` and `tapRefused(id)`, `startNewConversation`, `send(text, action, replyTo)`, `retry(pendingUuid)`, `discard(pendingUuid)`, `upload(source, fileName, mimeType, id)`, `dismissUpload(id)`, `setTyping`, `pressButton`, `submitPreChat(values)`, `submitEmail(email)`, `cancelGate`, `gateBeforeChat`, `endConversation`, `markResolved`, `submitCsat(rating, comment)`, `requestTranscript(email)`, `identify`, `logout`, `setLanguage`, `setPushToken(token)`, `isOnScreen(conversationId)`, `absoluteUrl(link)`, `fetchFile(link, maxBytes)`, and `help`.

Every action is safe on the main thread and answers at once; nothing a screen calls waits for a delivery. `send` and `pressButton` return a `SendOutcome`: `Queued(uuid)` (a pending row exists, delivery runs in the background), `Held` (the text waits in `thread.heldMessages` for the step before the chat) or `Refused(SendRefusal)` with `EMPTY`, `CLOSED`, `NOT_READY`, `TOO_LONG`; nothing is dropped without one of them. `retry`, `submitPreChat` (problems per field) and `submitEmail` (a `FieldProblem?`) answer at once too. `markResolved`, `upload`, `endConversation`, `submitCsat` and `requestTranscript` suspend and return their result; the UI only listens for it in a callback.

What the state adds for the UI: `SessionState.failure: SessionFailure?` (`UNKNOWN_WIDGET`, `NO_CONNECTION`, `IDENTITY_CHECK`, `SERVER`), set only while `phase == FAILED`, and `SessionState.offline`, which is something else (as on iOS): a call of the session reached no server at all (no network, a timeout); any answer clears it, a refusal included, and an answer that was not the route's (a captive portal's page, a redirect, `MalformedAnswer`) changes nothing. Every call of the engine reports to it (`noteAnswer`, `NetworkFailure.isNoConnection`). The UI shows a quiet line and the poll keeps trying. `ThreadState.heldMessages` (oldest first), `pending` with each row's `conversationId` (only the rows of the thread on screen), `botTypingRowId` (the bot's typing placeholder, so its answer fills the typing row in place), `UploadState` with `progress` (0 to 1; 1 once stored), `mimeType`, `startedAt` (wall time of the pick) and `messageId` (the stored message the upload became) under the id the UI gave `upload` (lower case, the row key from the pick to the stored message), `WidgetConfig.widgetPosition` (the launcher's side) and `WidgetConfig.launcherTitle` (the owner's launcher text, null while the owner kept the default).

## UI

The native messenger in the inbox's design, behind the `MessengerDesign` seam: Plain, Welcome or Direct, as the dashboard names them. The config's `widgetDesign` says `klartext`, `empfang` or `direkt`, and the code keeps those names (`KlartextDesign`, `EmpfangDesign`, `DirektDesign`, `ui/design/Empfang.kt`, `Direkt.kt`). Classic Views built in code, no Compose, no AppCompat, no Material Components. Package `com.deskwoot.sdk.ui`.

- **Row model.** `ThreadRows.build` turns the session state into `ThreadRow`s (day line, activity line, divider, incoming and visitor bubbles, upload, typing, choice, start and fixed buttons, CSAT, transcript) with the web's grouping, who lines, faces, tails, times and day rules. Each row has a stable key: `m:<id>`, `u:<clientAssignedUuid>` (the optimistic bubble and its stored row are one row), `qr:<answer id>` ("Frage geklärt"). The bot's typing row takes the key of its placeholder row, so the answer fills it in place.
- **Theme.** `Palette` is the web messenger's palette ported exactly (test vectors in `PaletteTest`); `UiColors` adds the neutral tokens, light and dark. Light or dark follows the presenting Activity's night mode (`Deskwoot.Theme.SYSTEM`), or `LIGHT`, `DARK`, `INBOX` (`config.widgetTheme`).
- **Strings.** Generated `strings.xml` files (10 languages, German "Sie" in `values-de/strings_formal.xml`), plus `strings_sdk.xml` for the few lines only the SDK needs. `Strings` reads them through a configuration context of the SESSION's language (`SessionState.locale`), never the device's, and switches to the `_formal` names when the inbox says "sie".
- **Entries.** `present*`, a notification tap and the in app card hand the Activity one pending `Entry` (a newer one replaces it, also through `onNewIntent`, which makes it the Activity's intent; a recreate keeps a pending one in the saved state). A notification's `Entry.Open` carries the push's visitor key and the time the tap arrived: `ACTIVE` opens once `identitySettled` (the server's first empty poll answer, `tapRefused`, still ends on the start page), `DORMANT` waits under the loading state for `identify` at most 10 s from the tap, `FORGOTTEN` or no key shows the start page. The in app card's `Entry.Open` has no key and waits for `ownsConversation`. `Entry.Conversation` opens the newest running conversation; before the visitor's conversations are known (`visitorLoaded`) it enters the empty thread without marking it new, so a restore still to come brings the running one. The tap's intent names the widget token (a tap after the process ended sets up that inbox at once, `Deskwoot.setupNow`) and has the conversation as its data (one PendingIntent per conversation). A tap that would make the messenger the root of a new task starts the app's launch Activity under it and ends that instance.
- **End of a visitor.** The engine's `visitorWiped` hook runs on the main thread inside the call that ended the visitor; the facade and the Activity reset there (screens, viewer, picks, the pending entry), and a state with an older `visitorGeneration` is never drawn again.
- **A new look.** A change of language, brand, design or help center builds the screens again (`Messenger.rebuild`); a change of design translates the trail first (`LookSwitch`: Direct's chat is its start page, Plain and Welcome have a thread screen), and each new screen takes the saved state of the old one that showed the same thing.
- **Design seam.** `MessengerDesign` answers what the start screen is, which header a screen gets (`HeaderStyle`: Plain's sub header, Welcome's bar and its chat header on the band, Direct's sheet head), the canvas and the incoming bubble color, how choice and fixed buttons look (`ChoiceStyle`), the composer strip (`ComposerStyle`), which views carry Welcome's tab bar and which open as Direct sheets. The Activity's screen factory picks the screen per design: Plain's `HomeScreen`, Welcome's `EmpfangHomeScreen`, or for Direct the `ThreadScreen` as the start page with `DirektHeader` and the greeting block row; a sheet route is wrapped in `SheetScreen`. `Messenger` keeps the chat visible under an overlay screen (`Screen.isOverlay`), slides only the first sheet up and the last one down, and the `Navigator` never treats a sheet as a top level view. In Direct a thread route shows on the start page (`designRoute`). Screens over Welcome's band ask for light status bar icons (`Screen.barsOnBand`).

## Rules that hold everywhere

- Dependencies at runtime: `kotlinx-coroutines-android`, `androidx.annotation`, and for the UI `androidx.core`, `androidx.activity` and `androidx.recyclerview`, each without `androidx.profileinstaller` (androidx.core reaches it through lifecycle-runtime; it would add a startup ContentProvider and an exported receiver). JSON with `org.json`, HTTP with `HttpURLConnection`.
- Nothing runs before `Deskwoot.setup` (except `logout`, which deletes what an earlier launch stored), and `setup` itself does no disk, network or system service work on the main thread: the store folder, the manifest's base URL and the first foreground check are read on `Dispatchers.IO`. It may be called from any thread, at any time, more than once; in a process that is not the app's default one (`AppProcess`) it waits until that process shows the messenger or handles a push (`Deskwoot.activeSession`). The SDK's only ContentProvider is `DeskwootFileProvider`, which keeps the application context and nothing else; no reflection on the app's classes.
- Built for apps on older toolchains: Kotlin language and API version 2.0 (the oldest the 2.4 compiler accepts; 1.9 is refused), the 2.0 standard library as the dependency, `minCompileSdk` 24 in the AAR metadata, no consumer ProGuard rules.
- The developer log is off by default: `Deskwoot.logLevel` (`NONE`, `ERRORS`, `DEBUG`). At `ERRORS` the SDK writes one `[Deskwoot]` line per thing a developer must fix (unknown widget token, refused identity and why). `LogRedaction` masks anything shaped like a bearer, token or signature.
- State lives on the main thread (`Dispatchers.Main.immediate`); network and disk run on `Dispatchers.IO`. The engine publishes `SessionState` at most once per main loop turn (posted on `Dispatchers.Main`).
- Everything of one visitor (poll, stream, timers, sends, cache writes) runs in an identity scope that `logout` and a user switch cancel as a whole. `ChatSession.stop` cancels the rest.
- The bearer (`contactIdentifier`) is a secret: it goes into requests and the visitor file, never into logs, `toString` or the state.
- Only the application context is held; `ForegroundTracker` keeps identity hashes of started activities, never an Activity.

## Files on the device

They live in `noBackupFilesDir/deskwoot/`, named by the first 32 hex characters of the SHA-256 of the widget token, and are written to a temporary file that replaces the old one.

- `<key>.visitor.json`: `{ "v": 2, "widgetToken", "bearer", "verifiedExternalId", "lastReadAt" (ISO 8601 UTC), "lastConversationId", "pushRegistered" }`. `pushRegistered` is written before the first registration request for that bearer leaves the device and goes with the bearer; a file without it (also one of an older version) sent no registration. A `language` field of an older file is ignored.
- `push-removals.json` (one for every inbox of the app): `{ "v": 2, "removals": [{ "widgetToken", "bearer", "at" (ISO 8601 UTC) }, oldest first, at most 8 per inbox] }`, the registrations still to be removed; deleted once empty, a record older than 30 days is deleted unsent. It is not deleted with the visitor: it outlives them on purpose. An older version's `<key>.push-removals.json` is deleted unread.
- `<key>.cache.json`: `{ "v": 1, "identity": "anonymous" | "verified:<externalId>", "config": {raw config}, "conversationId", "messages": [raw server rows, at most 200], "conversations": [list entries], "segments": [{ id, status, resolvedAt, createdAt }], "resolved", "continuesAfterResolve" }`

The pictures and files of the chat live in `cacheDir/deskwoot/`, which Android may clear at any time:

- `images/`: the picture and file cache, named by the first 32 hex characters of the SHA-256 of its key (an attachment's id), at most 50 MB (the oldest go first). A download goes to a `dw-*.part` file next to its target and is moved into place only when no end of a visitor came meanwhile (`VisitorFiles`).
- `shared/`: copies under their own names that other apps open or share through `DeskwootFileProvider`, at most 50 MB; `shared/camera/` holds the shot the camera app writes into.
- `shared/temporary/`: a cookieless inbox's copies for opening or sharing a file, downloaded for that alone; deleted when the messenger closes for good and at the first setup of each process.
- `temporary/`: a cookieless inbox's pictures pass through here on their way into memory, each file deleted as soon as it is decoded; the folder goes at the first setup of each process too.
- `uploads/`: scaled photos made for an upload, deleted once their upload ended; one an ended process left behind goes at the first setup.

A cookieless inbox's pictures never go into `images/`, and its files to open or share go only to `shared/temporary/`.

Every change of these files, and the deletion of the pictures and file copies of the chat (`cacheDir/deskwoot/`), runs on one queue of the process (`StoreQueue`), in the order asked for and in a scope no session's `stop` cancels; a session's start waits for every step asked for before it. A logout or a change of the identified user deletes the visitor file and the cache, after their bearer went into the pending removals when its record says a registration was sent (a bearer no registration was sent for leaves nothing). A logout also ends the stored visitors of the app's other inboxes (`StoredVisitors.forgetAll`), and before `setup` (the application context comes from `DeskwootFileProvider.onCreate`) those of every inbox; on the main thread it waits up to 200 ms for those steps. A new visitor (a placeholder) writes no cache, so a dormant verified identity's files stay untouched until the app names its user. A cookieless inbox writes neither and deletes both, and keeps its registration flag and its removal in memory only. The messenger's saved state carries the visitor key of the visitor it showed (`none` for nobody); after a process death it comes back only when `ChatSession.ownsSavedState` says that visitor is the session's.

## Another server

The base URL is `https://deskwoot.com`. Deskwoot's own example apps point elsewhere with a manifest entry, read once, off the main thread, before the first request:

```xml
<meta-data android:name="com.deskwoot.sdk.BASE_URL" android:value="http://10.0.2.2:3000" />
```

Unit tests set `DeskwootInternal.baseUrl` or build the engine with a fake `HttpClient`.

## Build and tests

AGP 9 compiles Kotlin with its built in support; the root build file pins Kotlin 2.4.0 by declaring the Kotlin plugin with `apply false`. Warnings fail the build (the one warning that version 2.0 is deprecated is suppressed with `-Xsuppress-version-warnings`). Gradle's file system watching is off for this project: it missed edits made outside an IDE.

```sh
./gradlew :deskwoot:assembleRelease :deskwoot:testDebugUnitTest --max-workers=4
```

The engine tests run on virtual time (`kotlinx-coroutines-test`) against `FakeHttp`, `FakeRealtime` and the in memory store (`src/test/.../TestSupport.kt`), with Android's own `org.json` (`com.vaadin.external.google:android-json`), so JSON behaves as on a phone. No test touches the network. The UI's pure logic (palette, strings in every language, formats, markdown, link cards, rows, people, navigation) has JVM tests in `src/test/.../ui/`; they read the real string files.

`LiveSmokeTest` runs only when the environment names a server: `DESKWOOT_TEST_BASE_URL`, `DESKWOOT_TEST_WIDGET_TOKEN`, and `DESKWOOT_TEST_EMAIL` for an inbox that asks for an email first. It loads the config, sends a first message, polls until its row is back and restores it in a fresh session with the same store.
